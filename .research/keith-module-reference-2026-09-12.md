## Decisions for the new schematic

1. **Preserve the meaning of framing.** It is a transport codec. Immutable model context is compiled by supporting `context` infrastructure, after attention selection. No new model-attention claim follows from byte framing.
2. **Preserve diagnosis and execution as different improvement responsibilities.** Meta-harness diagnoses/evaluates. Self-evolution stages and operationally promotes/reverses code/harness revisions. Ordinary process supervision is supporting `runtime` infrastructure.
3. **Keep both attention interfaces explicit.** `evaluate_initiative()` preserves proactive policy; `select_context()` is a proposed extension for evidence/focus allocation. Initiative produces candidates; attention recommends their disposition; common work admission controls actual execution.
4. **Make consolidation of runtime ownership explicit.** The proposed scheduler combines temporal scheduling with common work admission and allocations. The reference distributes related responsibilities among scheduler, action-store and resource-governor. That consolidation is a new architectural choice, not a discovered property of its scheduler crate.
5. **Keep execution backends under the common action contract.** Tool-runner retains rooted filesystem and restricted process responsibilities; a new dispatch facade above these backends provides the universal invocation/attempt/result contract for all registered executors.
6. **Separate static catalog facts from refreshed observations.** Provider identity/authentication/transport defaults remain static declarations. Dynamic model/capability/availability records are a proposed catalog extension with independent freshness/versioning.
7. **Retain domain breadth.** Profile scope, goal budgets, commitment wakes, skill package synthesis, child messaging/workspaces/liveness, plugin migration and code evolution are explicit parts of v0.2. Python subprocess versus WASM plugin execution remains a backend decision; a manifest enum alone is not proof of a working backend.

Durable waiting is a supporting capability even though it was not in the 23-name list. The reference has a separate [waiting model](/root/agent-keith/crates/waiting/src/lib.rs:20) and [registration/recovery service](/root/agent-keith/crates/waiting/src/lib.rs:241). In the new design it belongs to scheduler subscriptions, while goals/commitments own why work is waiting.

The current-source review establishes module intent and source presence. It does not establish performance, successful deployment, or correctness of every execution path. No reference-system tests, services or builds were run.
