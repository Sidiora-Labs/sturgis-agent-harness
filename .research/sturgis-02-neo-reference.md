# Neo reference audit for Sturgis 02

Date: 2026-09-12. Reference root: `/root/private-neo-v1`.

This is a read-only inspection of current source in `client/`, `neo/`, `engine/`, `gateway/`, `neo-api/` and `router/`. It inventories features and deployment implications for discussion. It does not select Sturgis UI technology, establish an implementation spec, import donor code, or change Sturgis 01 qualification.

The root is **not a Git checkout** (`git rev-parse --show-toplevel` failed). The nested `client/` checkout reports branch `main`, HEAD `35cf27df30f3b85e7188cfc15140515ae058972b`. That commit identifies the client checkout, not the other directories or a clean working tree. Selected inspected source hashes are recorded below.

Codify surveys were used for discovery, followed by targeted `rg` and numbered source reads. Broad surveys span overlapping prefixes and can truncate; the findings below rely on the cited source, not survey completeness. Credentials, environment values, runtime databases, user content and prior memories were not read. No builds, tests, services or deployments were run, and no donor source was edited.

**Evidence classification:** “Source-confirmed” means a concrete implementation or integration call was inspected. “Surface only” means a client, registration or interface proves discoverable breadth but not a functioning deployment. **No feature was newly runtime-qualified by this audit.** Existing qualification, if any, is neither asserted nor invalidated here.

## Important limits and adaptation risks

1. **Multiple contracts must not become multiple Sturgis authorities.** Native WebChannel, Workmates and the public API have separate auth, event, scheduler and resource contracts. The useful reference is the behavior and boundary, not wholesale aggregation of their controllers. The source-area table identifies those owners.
2. **Local browser network policy is deliberately permissive.** The browser blocks link-local/cloud metadata targets but intentionally permits loopback and RFC1918/LAN targets; without an execution context it can also use a shared service. [Policy and service selection](/root/private-neo-v1/neo/agent/tools/browser/browser_tool.py:130). A hosted adaptation needs tenant-isolated browser processes/profiles and an intentional network policy for sandbox-local applications.
3. **Quota accounting must retain observed truth.** The public API metering finalizer rejects inactive/expired reservations and can raise `QuotaExceeded` before inserting usage when final actual usage exceeds remaining quota. [Finalization](/root/private-neo-v1/neo-api/packages/metering/neo_metering/service.py:180). This is a material mismatch with Sturgis 01's factual overage accounting. Adapt reservation concepts while keeping late/over-budget receipts durable and blocking subsequent allowance separately.
4. **A registered feature is not a qualified user path.** Channel factory breadth, mobile screens, MCP routes and provider-backed app catalog calls do not prove accounts, binaries, infrastructure or external callbacks currently work. No donor runtime was contacted during this audit.
5. **Extraction and evidence gates have precise limits.** The inspected library reader has no PDF branch, and media metadata is not transcription or visual understanding. Research citation validation establishes ID integrity and a review gate, not source entailment. Avoid broader product claims without a separately inspected and qualified implementation.
6. **Portability is narrower than full runtime migration.** The inspected content import excludes live authority and significant conversation/channel state. Any future “move between hosted and self-hosted” promise needs an explicit data and authority contract; current content migration code is only a partial reference.

The strongest adaptation candidates are durable chat replay, explicit run/delivery status, scoped artifact access, revision-bound app permission review, browsable knowledge provenance, user-visible schedules/attention, and private-runtime routing. The broad developer API/SDK platform, native mobile app, wallet/financial product surfaces, and all-provider/all-channel breadth are candidates to defer until the desired Sturgis product scope is chosen. These are recommendations for discussion, not approved implementation work.
