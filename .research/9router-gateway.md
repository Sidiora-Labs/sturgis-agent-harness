# 9router gateway reference audit

Inspected on 2026-09-12. Reference repository: https://github.com/decolua/9router. Source pin: `17c4cc76877bd1755030a8414f8d0083f48dcccf`; package version `0.5.75`. Read-only source checkout: `.research/9router-reference/`. This is a source audit; no upstream provider login, inference request, billing action or upstream service was executed. Source presence is not live provider qualification.

## Architectural conclusion

9router is an independent model gateway with its own connections, credentials, model catalog, aliases, routing groups, consumer API keys and usage records. Agents and CLI tools consume its inference API. There is no agent-owned provider table in its persistence schema. Sturgis should preserve this division: the gateway owns provider connectivity and routing; agents select gateway models and authenticate as clients. The gateway can be embedded as an independently composed subsystem or served as a separate process without depending on an agent runtime.

The upstream repository is MIT licensed, copyright 2024–2026 decolua and contributors. If implementation copies substantial upstream source, retain its copyright and full permission notice. This audit does not copy implementation source into Sturgis. The repository license does not establish availability, provider eligibility, API pricing or service-specific authorization.

## Source and deployment topology

- `package.json`: private Next.js 16/React 19 application with a separately packaged `cli/` launcher. `open-sse/` is source within the repository, consumed through aliases; it is not a separately versioned published package in this checkout.
- `custom-server.js`: wraps the HTTP listener to stamp trusted peer metadata, handles an h2c downgrade case, and starts proactive token refresh. Next standalone output and a source checkout both use this server.
- `next.config.mjs`: public `/v1/*` rewrites lead to app routes under `src/app/api/v1/*`; `/v1beta/*` supports Gemini-style requests. These coexist with management routes and the dashboard.
- `Dockerfile`: Node 22 image, built standalone Next application, runtime port 20128, persistent `DATA_DIR`, server process running as user `node` through its entrypoint. Native SQLite is optional; a sql.js fallback is shipped.
- `docker-compose.yml`: the gateway container, persistent `/app/data`, and a separate Headroom compression container. Headroom is an optional feature dependency, not a model provider or the primary gateway.
- `src/lib/dataDir.js` and `src/lib/db/paths.js`: gateway-local `DATA_DIR/db/data.sqlite`, backups under `DATA_DIR/db/backups`; default data root `~/.9router` on Unix and AppData/9router on Windows. Old JSON stores are legacy migration inputs.
- `src/lib/db/schema.js`: SQLite WAL, foreign keys and busy timeout; schema tables own settings, provider connections, custom nodes, proxy pools, consumer API keys, combos, KV records, request details and usage. No tenant/agent key appears in these tables, so hosted tenant isolation would require an explicit Sturgis design rather than inheriting it from this local-first upstream schema.
- Optional cloud sync orchestration is present, but the remote cloud service implementation is outside this repository. A README deployment claim about cloud targets is not equivalent to a fully inspected hosted gateway implementation.

The upstream `docs/ARCHITECTURE.md` is dated 2026-02-06 and still describes JSON persistence; the current schema/paths above take precedence.

`providers/schema.js` explicitly labels its `resolveProvider` transport-default resolver as not wired into runtime. Do not treat every documented default there as active behavior. Runtime `providers/index.js`, service routing and executors are the authority.

## Inference path and retries

1. Compatibility route initializes translators and invokes `src/sse/handlers/chat.js`.
2. Handler parses JSON; extracts the client gateway key; checks it when configured; resolves model/alias or a routing group. Request endpoint and body determine input format.
3. For a combo, the gateway chooses fallback, round-robin/sticky rotation, or fusion. Required input capabilities affect ordering. `detectRequiredCapabilities` has search auto-switch explicitly disabled in this pin; do not advertise it as wired.
4. `getProviderCredentials` selects an active account under a process mutex. It excludes already attempted accounts, model cooldowns and cached exhausted quota. Fill-first, round-robin and sticky rotation can select connections. Public no-auth providers get a virtual connection.
5. `checkAndRefreshToken` prepares current credentials; some Google providers also resolve a project id. Background refresh runs independently of requests, and refresh locks/deduplication protect rotating tokens.
6. `open-sse/handlers/chatCore.js` optionally transforms context, detects target format, invokes a translator, and selects a provider executor. The base executor accepts endpoint overrides, provider headers, abort signals, connection timeouts, retry policies and proxy configuration.
7. Executors own special protocol behavior. ChatCore can refresh and retry on 401/403 for credentialed providers. Account failures can move to another account; combo failures can move to another model. These are three distinct retry layers: request/endpoint, provider account, model combo.
8. SSE or JSON output is translated back to the original client format; success/error and usage are recorded. Initial success returns a response stream: this does not prove a failed partially emitted response can be invisibly replayed. Sturgis must define a no-replay-after-visible-output boundary.

`open-sse/services/accountFallback.js` and `config/errorConfig.js` match error text/status to cooldown decisions, with exponential quota backoff. `src/sse/services/auth.js` persists model locks and special reset rules; Antigravity has an additional RAM quota cache. `services/combo.js` keeps rotation state in process memory. These in-process locks/caches are not distributed coordination primitives.

## Authentication modes: not one generic API-key field

| Mode | Current source providers | Required mechanics |
| --- | --- | --- |
| API key/token | API-key registry entries and dual-auth providers | Header-specific authorization; endpoints and provider model metadata; optional account/project/region fields. Anthropic uses its header/version contract, Gemini its key contract, and media providers may use Basic, Token, custom headers or AWS SigV4. |
| OAuth authorization code with PKCE | Claude Code (`claude`), Codex, xAI, GitLab | Browser authorization, state, verifier/challenge, token exchange, callback origin and token refresh where supported. GitLab supports metadata for self-hosted base URL/client id. |
| OAuth authorization code | Gemini CLI, Antigravity, iFlow, Cline, ClinePass, Zed; inactive Trae/Windsurf | Provider-specific authorization URLs, callback and exchange; Zed encodes an RSA private-key verifier rather than using a plain PKCE verifier. |
| Device authorization | GitHub Copilot, Kiro, Kimi, Kilo Code, Qoder, CodeBuddy CN/Intl, Grok CLI | Device code, verification URI/user code, expiry and polling; Kiro additionally registers an AWS OIDC client and retains region/identity-center details. |
| Browser token | Kimchi | Browser returns a token; dedicated validation and user lookup. This is not an OAuth refresh-token flow. |
| Imported token | Cursor; additional import routes for Codex/Kiro/Grok CLI | Explicit credential import with provider account metadata. Cursor source notes no public refresh endpoint; it must not promise automatic refresh. |
| Browser cookie | Grok Web, Perplexity Web | Cookie-specific requests and specialized executors. These are not generic documented chat APIs. |
| Custom encrypted callback | Xiaomi MiMo | X25519 ECDH plus AES-GCM callback decryption in its dedicated helper, or explicit API key. The helper is separate from the generic OAuth provider map. |
| Service account / platform credential | Vertex and partner models | Service-account JSON JWT exchange, project/region and token cache; a trial credit offer is not an indefinitely free API. |
| No authentication | OpenCode Free, MiMo Free; local/media services | Endpoint-specific protocol and selected available models. A no-auth flag is not proof of stable service or free access to every returned model. |

Additional Kiro routes support social identity-provider authorization/exchange, imported credentials, CLI proxy import, and API keys. The registry explicitly permits dual OAuth/API-key modes for Kimi, Kimchi, Qoder, ClinePass, CodeBuddy CN/Intl, xAI and Xiaomi MiMo. Raw token imports must not be approximated by silently reading another application's private credential files.

The generic OAuth map has 22 provider entries, including Trae and Windsurf whose registry entries are not currently imported. Xiaomi's custom helper and specialized import routes add paths beyond that map. Registry category is a display grouping, not a complete authentication contract: for example Kiro is category `free` but requires login; `xai` is category `oauth` and also supports API keys.

## Specialized executors and compatibility boundary

`open-sse/executors/index.js` registers dedicated executors for Antigravity, Azure, Gemini CLI, GitHub, iFlow, Qoder, Kiro, Kimchi, Codex, Cursor, Vertex/Vertex Partner, OpenCode Free/Go, Grok Web/CLI, Perplexity Web, local Ollama, CommandCode, Xiaomi token plan/MiMo/free, CodeBuddy CN/Intl, Trae, Zed, Windsurf and Devin CLI, with a handful of aliases. Other providers fall through to the default executor.

The translator supports an OpenAI intermediate path with request/response adapters for Anthropic, Gemini, Responses, Cursor, Kiro, Vertex, Antigravity, Ollama and CommandCode. Tool calls, partial chunks, finish reasons, multimodal blocks, thinking/reasoning, usage and model quirks have separate concerns. Adding a preset is therefore insufficient for a protocol with a specialized executor.

A provider can be integrated faithfully in Sturgis by implementing its authentication lifecycle plus native executor/translation, or by connecting an existing independent compatible gateway such as 9router and importing its exposed model ids. A gateway bridge provides reach to the configured upstream accounts but must not be labelled native OAuth integration. No direct integration was implemented during this audit.

Further current-source corrections used for the Sturgis catalog:

- [GitHub's official notice](https://docs.github.com/en/github-models) states that GitHub Models, its catalog, inference API and BYOK retired on July 30, 2026. It is omitted as a direct preset. GitHub Copilot is a separate product; the upstream Copilot sign-in flow remains a distinct reference path.
- [Hugging Face's current chat documentation](https://huggingface.co/docs/inference-providers/tasks/chat-completion) uses `https://router.huggingface.co/v1`; the upstream Hugging Face registry primarily declares media service adapters.
- [Cohere's compatibility documentation](https://docs.cohere.com/docs/compatibility-api) uses `https://api.cohere.ai/compatibility/v1`, so copying the upstream registry's older chat URL would give the wrong generic connection base.
- [Z.AI's official API introduction](https://docs.z.ai/api-reference/introduction) distinguishes standard `https://api.z.ai/api/paas/v4` from its separate coding-plan endpoint. The preset uses the standard API.
- [MiniMax's Messages endpoint](https://platform.minimax.io/docs/api-reference/text-chat-anthropic) and [model discovery endpoint](https://platform.minimax.io/docs/api-reference/models/anthropic/list-models) are `https://api.minimax.io/anthropic/v1/messages` and `/models`, respectively. The gateway stores the base ending in `/anthropic/v1` because it appends the operation itself; SDK documentation sometimes gives `/anthropic` because that SDK appends `/v1`.
- MiMo Free is not a generic unauthenticated Chat Completions server. Its [specialized executor](https://github.com/decolua/9router/blob/17c4cc76877bd1755030a8414f8d0083f48dcccf/open-sse/executors/mimo-free.js) bootstraps a JWT with a device fingerprint, sends browser-like identity headers and injects a MiMoCode identity marker to satisfy an upstream anti-abuse check. It is recorded in the inventory, not offered as a misleading direct preset. An explicitly configured external gateway can expose its own namespaced models.

The resulting Sturgis catalog is independent metadata in `model_gateway/catalog.py`. It supplies 34 connection presets including four protocol-specific custom endpoints. All fallback model defaults are conservative values (8,192 context tokens, 1,024 output tokens, tools disabled); catalog presence does not set the model as ready. Tests exercise JSON serializability, independent copied records, endpoint syntax and prefix preservation, protocol separation, retired/specialized-provider omissions, and import without either the `agent` or `consumer` package.

A read-only unauthenticated `GET https://opencode.ai/zen/v1/models` from the build host on the inspection date returned HTTP 403. No inference or identity-header spoofing was attempted. This records a host-specific discovery failure, not proof that the service is unavailable everywhere. The connection flow must report this error and permit another provider or deliberate manual import; do not replace it with a fabricated live catalog. Catalog tests passed: 86 tests, 100 percent catalog statement/branch coverage, measured in `.build/gateway-catalog.coverage`.
