# Hermes reference inspection for Sturgis 02

Inspected 2026-09-12. This is a source inventory, before interface or specification decisions. It does not select a Sturgis architecture or claim Hermes runtime qualification.

**Finding:** the current official Hermes source is a broad personal-agent product: Python CLI, terminal UI, Electron desktop, browser dashboard, messaging gateways, API adapters, persistent sessions, editable skills and memories, automation, and remote execution. It also contains substantial hosted-runtime integration—including relay provisioning, multiple profile scopes, managed cron, and machine sleep/wake coordination. Describing this checkout as only a terminal agent, or as having no hosted support, would omit implemented features. Its own security policy nevertheless defines the agent process as a single-tenant personal trust envelope; profile routing and credential scopes are distinct from OS containment.

## Setup, identity, credentials, and profiles

The setup command supports a full wizard or selected model, TTS, terminal, gateway, tool, telemetry, and agent sections; noninteractive, reset, reconfigure, quick, and Portal flows are explicit parser options. Provider authentication is a separate subsystem with provider registry, auth store, credential pools, OAuth flows, cross-process locking, and atomic restricted-permission writes. These are source mechanisms, not verified external logins. [Setup parser](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/subcommands/setup.py:8), [authentication subsystem](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/auth.py:1).

Profiles are filesystem-backed identities with separate homes for configuration, secrets, memories, sessions, skills, logs, workspace, and cron. Clone behavior is deliberate: curated memory/persona can be copied, while conversation history and cron jobs are excluded from the broader clone path to avoid inheriting private history or duplicate scheduled work. Export also has an explicit file allow-list. [Profile layout and clone policy](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/profiles.py:24), [clone exclusions](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/profiles.py:50), [export policy](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/profiles.py:100).

Current Hermes additionally implements an **opt-in multiplexing gateway**, rather than requiring one gateway process per profile. It combines profile routes, home overrides, and context-local secret mappings; unscoped credential reads fail closed when multiplexing is enabled. The runtime enables this mode at gateway construction and hydrates profile secrets in scoped execution paths. Platform routing considers bot/profile boundaries and channel/thread specificity. These are real application scopes, but all served profiles still share a Python process and event loop. [Multiplex design](/tmp/sturgis-02-hermes.GYdNrn/docs/design/multiplexing-gateway.md:1), [secret-scope implementation](/tmp/sturgis-02-hermes.GYdNrn/agent/secret_scope.py:1), [runtime integration](/tmp/sturgis-02-hermes.GYdNrn/gateway/run.py:1747), [mode activation](/tmp/sturgis-02-hermes.GYdNrn/gateway/run.py:3424), [profile routes](/tmp/sturgis-02-hermes.GYdNrn/gateway/profile_routing.py:55).

Dashboard authentication defines interactive sessions with user, organization, provider, and expiry fields, and scoped token principals; middleware enforces the configured authentication path. This is identity and request-admission machinery, not evidence of complete tenant provisioning or OS isolation. Also, `HERMES_MANAGED` specifically denotes package-manager-managed installations such as Nix; it must not be mistaken for a hosted-customer flag. [Auth types](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/dashboard_auth/base.py:9), [middleware](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/dashboard_auth/middleware.py:148), [managed-install meaning](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/config.py:248).

## Memory, knowledge, and session continuity

Built-in curated memory uses bounded `MEMORY.md` and `USER.md` files. `MemoryStore` holds live editable entries while freezing the system-prompt snapshot at load time for prefix-cache stability; constructor defaults are **2,200 and 1,375 characters**, not tokens. An update can therefore change persisted memory without immediately rewriting the already-loaded prompt prefix. [Memory representation](/tmp/sturgis-02-hermes.GYdNrn/tools/memory_tool_store.py:1), [snapshot and limits](/tmp/sturgis-02-hermes.GYdNrn/tools/memory_tool_store.py:66).

Built-in memory may coexist with one selected external provider. Memory-provider discovery is category-specific and home-aware: shipped providers take precedence over user/project/entry-point duplicates, project providers require opt-in, and `memory.provider` selects one external implementation. The inspected tree includes optional provider implementations for Honcho, Hindsight, Mem0, OpenViking, Supermemory, ByteRover, RetainDB, and holographic memory. Directory presence does not mean these providers are enabled or available without their dependencies and configuration. [Memory manager](/tmp/sturgis-02-hermes.GYdNrn/agent/memory_manager.py:1), [provider discovery and precedence](/tmp/sturgis-02-hermes.GYdNrn/plugins/memory/__init__.py:1).

Session history is structured SQLite state: sessions carry source, user/chat/thread identity, parent lineage, model configuration, workspace/Git metadata, costs, activity, and profile name; messages carry tool calls/results, timestamps, effects, compression state, and display metadata. Session CLI supports filtering, exporting, deleting, and pruning. The current search tool performs FTS5 discovery, lineage deduplication, and direct detail/history hydration; its implementation explicitly states **no LLM calls**. This supersedes the README's older “FTS5 search with LLM summarization” description. [Session schema](/tmp/sturgis-02-hermes.GYdNrn/hermes_state_common.py:328), [message schema](/tmp/sturgis-02-hermes.GYdNrn/hermes_state_common.py:391), [session operations](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/subcommands/sessions.py:15), [current search tool](/tmp/sturgis-02-hermes.GYdNrn/tools/session_search_tool.py:1), [older README wording](/tmp/sturgis-02-hermes.GYdNrn/README.md:26).

The grounded knowledge surfaces are curated memory, searchable conversations, skill/reference libraries, and optional provider backends. A desktop memory-graph view is not by itself proof that all runtime knowledge is stored in one canonical graph.

## Installation, remote access, and hosted boundaries

**Self-host packaging is present in the core repository.** Python packaging, bootstrap installation documentation, Electron package scripts, and a first-party Dockerfile are distinct delivery surfaces. The current Dockerfile separates immutable application code under `/opt/hermes` from writable state under `/opt/data` and uses s6 supervision for the main process, dashboard, and per-profile gateways. Installation documentation covers bootstrap prerequisites and an unprivileged system-user mode; Nix is described as best-effort rather than a currently supported installation path. None of these install paths was executed. [Container layout/supervision](/tmp/sturgis-02-hermes.GYdNrn/Dockerfile:43), [installation guide](/tmp/sturgis-02-hermes.GYdNrn/website/docs/getting-started/installation.md:93).

**Remote and Cloud connections are actual desktop concepts.** The connection registry models `local`, `cloud`, `remote`, and `ssh`, with endpoint/auth details, organization identifiers, SSH parameters, and remote-profile selection. Token connections and OAuth cookie/WebSocket-ticket connections have different transport handling. Cloud discovery calls an external Portal `/api/agents` endpoint with an organization parameter. This is concrete client integration with a hosted service, not that service's implementation inside the desktop. [Connection schema](/tmp/sturgis-02-hermes.GYdNrn/apps/desktop/electron/connection-registry.ts:40), [connection authentication](/tmp/sturgis-02-hermes.GYdNrn/apps/desktop/electron/connection-config.ts:12), [Cloud discovery](/tmp/sturgis-02-hermes.GYdNrn/apps/desktop/electron/main.ts:8698).

**Relay supports a hosted gateway/connector split.** Agent-side enrollment and self-provisioning call an external connector, register an instance and optional wake URL, and handle per-gateway credentials. The current transport uses an authenticated outbound WebSocket for inbound delivery as well as requests, so a relay gateway does not require a public inbound message endpoint. Platform credentials and platform signature verification belong to the connector trust domain according to the cross-repository contract. Gateway-side source implements authentication, normalized-event admission, replay deduplication, media localization, egress discrimination, and dormant/reconnect controls. Connector-side tenant resolution, durable queues, and authorization remain external evidence obligations. [Provision client](/tmp/sturgis-02-hermes.GYdNrn/gateway/relay/__init__.py:329), [WS authentication](/tmp/sturgis-02-hermes.GYdNrn/gateway/relay/auth.py:1), [adapter connect/inbound](/tmp/sturgis-02-hermes.GYdNrn/gateway/relay/adapter.py:758), [relay contract](/tmp/sturgis-02-hermes.GYdNrn/docs/relay-connector-contract.md:77), [connector trust domain](/tmp/sturgis-02-hermes.GYdNrn/docs/relay-connector-contract.md:591). Relay authentication source still labels the integration experimental.

**Managed cron is implemented on the agent side.** The selectable Chronos provider reconciles enabled local jobs into external NAS one-shot schedules, sends idempotency keys, cancels obsolete schedules, and re-arms after completion; it does not run its own periodic wake loop. It uses the agent's Nous authentication rather than external scheduler credentials. The inbound fire verifier checks an asymmetric JWT, audience, expiry, configured issuer, and `cron_fire` purpose. The gateway persists a claim before returning `202` and dispatching background execution. The dashboard forwards to the owning gateway and re-verification path instead of executing jobs in its own process. External scheduler/NAS provisioning and actual wake reliability were not inspected or exercised. [Chronos implementation](/tmp/sturgis-02-hermes.GYdNrn/plugins/cron_providers/chronos/__init__.py:1), [JWT verification](/tmp/sturgis-02-hermes.GYdNrn/plugins/cron_providers/chronos/verify.py:41), [gateway admission](/tmp/sturgis-02-hermes.GYdNrn/gateway/platforms/api_server.py:3475), [dashboard forwarding](/tmp/sturgis-02-hermes.GYdNrn/hermes_cli/web_routers/cron.py:272), [external wire contract](/tmp/sturgis-02-hermes.GYdNrn/docs/chronos-managed-cron-contract.md:1).

**Scale-to-zero is more than a proposed relay primitive in this commit.** `gateway/scale_to_zero.py` and shutdown/startup integration implement opt-in idle detection, broad work/liveness checks, relay dormancy, reconnect hold, and either direct Fly Machines socket suspension or a NAS-brokered sleep request. Arming requires the Labs environment stamp, relay-only/absent messaging, and a registered wake URL. The watcher requires acknowledged dormancy, rechecks idle state, and stays awake on missing suspend capability or rejected transitions. Actual wake remains platform/connector-mediated. This supersedes relay-contract passages that still describe the idle decision and machine suspend as deferred behavior. [Enablement and idle predicate](/tmp/sturgis-02-hermes.GYdNrn/gateway/scale_to_zero.py:1), [suspend requests](/tmp/sturgis-02-hermes.GYdNrn/gateway/scale_to_zero.py:197), [watcher and transitions](/tmp/sturgis-02-hermes.GYdNrn/gateway/run_shutdown.py:432), [startup wiring](/tmp/sturgis-02-hermes.GYdNrn/gateway/run_startup.py:1324), [older deferred wording](/tmp/sturgis-02-hermes.GYdNrn/docs/relay-connector-contract.md:301).

**Tenant boundaries must be described at the right layer.** Current application scopes include profiles, users/organizations in dashboard auth, API profile prefixes, relay instance identities, and managed cron audience checks. These are meaningful mechanisms. The security policy still declares a single-tenant personal agent and identifies the operating system as the containment boundary against an adversarial model. Terminal-backend isolation covers shell/file operations; it does not contain the entire Python process, plugins, hooks, code-execution or MCP subprocesses. Whole-process containers or other OS wrappers address that larger boundary. This audit found implemented hosted-runtime contracts and clients, but did not find or inspect the external Portal/NAS billing, tenant provisioning, connector store, or complete hosting control plane. Their absence from this inspection is not evidence that the operated services lack those features. [Security model](/tmp/sturgis-02-hermes.GYdNrn/SECURITY.md:32), [containment distinction](/tmp/sturgis-02-hermes.GYdNrn/SECURITY.md:58), [whole-process wrapping](/tmp/sturgis-02-hermes.GYdNrn/SECURITY.md:90).

## Interpretation constraints for later synthesis

- Preserve the current product breadth across desktop, web, terminal, messaging, API, automation, media, and remote execution when comparing references.
- Keep persistent memory, searchable episodic history, procedural skills, and optional provider backends distinct. Source does not establish one universal canonical knowledge graph or model-weight learning.
- Keep profile scoping, authenticated hosted protocols, external control-plane responsibilities, and whole-process isolation distinct.
- Prefer the current implementation over stale README or contract fragments: session search no longer makes LLM calls; embedded dashboard chat is always on; Chronos now resides under `plugins/cron_providers/chronos`; scale-to-zero now has an idle/suspend implementation; retired relay delivery-signature helpers remain explicitly marked compatibility code.
- This report supplies source evidence only. No consumer flow, provider login, channel delivery, hosted wake, installation, tenant-isolation test, or operational reliability claim was qualified.
